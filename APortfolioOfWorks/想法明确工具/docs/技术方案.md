# 强引导式项目澄清工具技术方案

## 1. 项目定位

本项目是一个面向新手的强引导式项目澄清工具。

它帮助用户从一个模糊、混乱或功能过多的项目想法出发，经过 AI 追问、伪需求判断、MVP 收敛，最终生成一份可以直接交给 Codex、Claude Code 或其他 AI 编程工具执行的开发提示词。

本项目不是：

- 项目管理工具
- 游戏化闯关页面
- 低代码平台
- 通用 AI 聊天机器人
- 灵感生成器
- 课程或教程平台

本项目要做的是：

- 强制用户按正确顺序思考项目
- 阻止用户一开始就堆功能
- 判断项目是否可能是伪需求
- 引导用户修改不成立的想法
- 将可做的想法压缩成最小 MVP
- 输出可执行的 AI 开发提示词

一句话定义：

> 一个严肃的单页 AI 引导工具，帮助知道一点但不系统的新手，把模糊项目想法整理成可执行 MVP，并生成可直接交给 AI 编程工具的开发提示词。

## 2. 目标用户

第一版只服务一类用户：

> 知道一点项目开发概念，但不知道完整流程的新手。

典型状态：

- 只有一个模糊想法
- 想做很多功能，但没有主线
- 不知道一个项目应该先验证什么
- 不知道什么是 MVP
- 容易一上来就让 AI 写代码
- 容易把普通 AI、微信、表格、现有 App 能解决的问题误判成项目机会

暂不服务：

- 成熟创业者
- 专业产品经理
- 企业项目团队
- 需要多人协作的团队
- 想寻找大量项目灵感的人

## 3. MVP 目标

第一版 MVP 只验证一个核心闭环：

```text
用户输入项目想法
↓
AI 进行项目初诊并提出下一个关键问题
↓
用户逐步回答
↓
AI 判断是否存在伪需求风险
↓
如果不成立，引导用户修改想法
↓
如果基本成立，进入 MVP 收敛
↓
AI 输出完整开发提示词
```

MVP 成功标准：

- 用户不用自己懂产品流程，也能被引导完成项目澄清
- AI 能明确指出伪需求风险，而不是只鼓励用户继续做
- 输出结果足够具体，可以直接交给 AI 编程工具启动开发
- 页面体验严肃、清晰、低干扰

## 4. 第一版功能范围

### 4.1 必做功能

1. 单页引导式流程
   - 每次只显示一个核心问题
   - 用户回答后点击继续
   - 系统根据上下文决定下一步

2. AI 追问
   - 根据用户项目想法生成下一个最关键问题
   - 不做泛泛聊天
   - 不一次性抛出大量问题

3. 伪需求判断
   - 判断目标用户是否真实
   - 判断使用场景是否具体
   - 判断现有替代品是否足够强
   - 判断用户是否有打开新工具的理由
   - 判断是否只是自嗨

4. 打回修改
   - 如果想法不成立，必须直接指出原因
   - 给出修改方向
   - 让用户重新回答关键问题

5. MVP 收敛
   - 强制只保留一个目标用户
   - 强制只保留一个核心场景
   - 强制只保留一个核心流程
   - 强制砍掉非必要功能

6. 开发提示词生成
   - 生成可直接发给 Codex / Claude Code 的提示词
   - 包含产品定位、功能范围、页面结构、数据结构、验收标准

### 4.2 暂不做功能

- 用户账号
- 项目列表
- 历史记录
- 多项目管理
- 分享链接
- 团队协作
- 模板市场
- 付费系统
- 文件上传
- 知识库
- 多模型切换 UI
- 复杂工作流编辑器
- 游戏化关卡、积分、徽章、排行榜

## 5. 产品流程设计

第一版采用 5 个阶段。

### 阶段 1：项目初诊

目的：

确认用户到底想做什么。

核心问题：

```text
你想做一个什么项目？
请用尽量具体的话说明：
1. 给谁用
2. 在什么场景下用
3. 想解决什么问题
```

AI 判断重点：

- 是否只有一句空泛想法
- 是否能说清目标用户
- 是否能说清使用场景
- 是否能说清问题本身

可能输出：

- 继续追问目标用户
- 继续追问具体场景
- 继续追问问题频率
- 进入真实需求判断

### 阶段 2：真实需求判断

目的：

判断这个问题是否真实存在，还是用户脑补出来的。

典型问题：

```text
这个用户现在遇到这个问题时，通常怎么解决？
```

```text
为什么他现在的解决方式不够好？
```

```text
这个问题是一周会出现很多次，还是偶尔才出现一次？
```

AI 判断重点：

- 问题频率
- 用户是否真的在意
- 用户是否已经有更顺手的替代方式
- 这个问题是否值得专门做一个工具

### 阶段 3：伪需求审判

目的：

直接判断项目是否可能不成立。

审判维度：

- 普通 AI 是否能直接替代
- 微信/QQ/表格/备忘录是否已经足够
- 现有 App 是否已经覆盖
- 用户是否有动力打开新工具
- 使用频率是否太低
- 是否只是开发者自嗨
- 是否只是“有趣”，但不值得做产品

输出类型：

```json
{
  "verdict": "pass | revise | reject",
  "riskLevel": "low | medium | high",
  "reasons": [],
  "requiredRevision": ""
}
```

规则：

- `pass`：可以进入 MVP 收敛
- `revise`：想法有风险，必须修改后继续
- `reject`：当前版本不值得做，必须重构方向

注意：

第一版不做“永久失败”。即使被判定为 `reject`，系统也要引导用户修改想法，而不是直接结束。

### 阶段 4：MVP 收敛

目的：

把项目从“大而全想法”压缩成第一版能开发的最小闭环。

强制收敛项：

```text
第一版只允许保留：
1. 一个目标用户
2. 一个核心场景
3. 一个核心问题
4. 一个核心动作
5. 一个最终产出
```

AI 要主动砍掉：

- 非核心功能
- 社区功能
- 账号系统
- 复杂权限
- 多端适配
- 数据分析后台
- 模板市场
- 过早商业化功能

MVP 输出结构：

```json
{
  "targetUser": "",
  "coreScenario": "",
  "coreProblem": "",
  "coreAction": "",
  "finalOutput": "",
  "mustHaveFeatures": [],
  "cutFeatures": []
}
```

### 阶段 5：开发提示词生成

目的：

生成一份可以交给 AI 编程工具执行的完整提示词。

提示词必须包含：

- 项目背景
- 产品定位
- 目标用户
- MVP 目标
- 页面结构
- 核心流程
- 功能清单
- 明确不要做什么
- 数据结构
- AI 接口调用方式
- 验收标准
- 技术约束

输出格式：

```text
# 任务：开发 [项目名] MVP

## 项目定位
...

## 目标用户
...

## MVP 核心闭环
...

## 页面结构
...

## 功能要求
...

## 明确不要做
...

## 数据结构
...

## AI 接口
...

## 验收标准
...
```

## 6. 页面形态

第一版为单页 Web 应用。

### 6.1 页面布局

推荐布局：

```text
┌──────────────────────────────────────┐
│ 项目初诊工具                          │
│ 当前阶段：真实需求判断                 │
├──────────────────────────────────────┤
│                                      │
│ 当前问题：                            │
│ 这个用户现在通常怎么解决这个问题？      │
│                                      │
│ [ 多行输入框 ]                         │
│                                      │
│ [继续]                               │
│                                      │
├──────────────────────────────────────┤
│ 当前诊断摘要：                         │
│ - 目标用户还不够具体                   │
│ - 替代方式需要继续确认                 │
└──────────────────────────────────────┘
```

### 6.2 交互原则

- 一屏只问一个问题
- 不使用游戏化词汇
- 不用“恭喜过关”
- 不用积分、徽章、奖励动画
- 问题要短，但必须尖锐
- 诊断结果要直白
- 如果回答太空泛，必须要求重答
- 用户不能随意跳到最终提示词生成

### 6.3 状态展示

顶部显示当前阶段：

- 项目初诊
- 真实需求判断
- 伪需求审查
- MVP 收敛
- 开发提示词生成

底部显示当前诊断摘要：

- 已明确的信息
- 仍缺失的信息
- 当前风险
- 下一步为什么要问这个问题

## 7. 技术架构

### 7.1 推荐技术栈

第一版建议使用：

- 前端：React + Vite + TypeScript
- 样式：CSS Modules 或普通 CSS
- 后端：Node.js + Express
- AI 接口：阿里云百炼 OpenAI 兼容接口
- 数据存储：前期只用浏览器内存或 localStorage
- 部署：本地优先，后续可部署到 Vercel、阿里云或普通 Node 服务器

如果要进一步简化，也可以使用：

- Next.js 单体项目
- 或纯 Vite 前端 + 一个轻量 Node API 服务

### 7.2 为什么需要后端

不要在前端直接调用阿里云百炼 API。

原因：

- API Key 会暴露
- 无法统一控制模型参数
- 无法做请求日志
- 无法做安全过滤
- 后续不方便加入用户额度和审计

第一版后端只需要一个接口：

```text
POST /api/project/next-step
```

后续可以再加：

```text
POST /api/project/generate-prompt
```

但第一版也可以统一由 `next-step` 根据阶段返回不同结果。

## 8. 前端状态设计

### 8.1 核心状态

```ts
type Stage =
  | "initial_diagnosis"
  | "need_validation"
  | "fake_need_review"
  | "mvp_scope"
  | "prompt_generation";

type Verdict = "pass" | "revise" | "reject" | "pending";

type Message = {
  id: string;
  role: "user" | "assistant";
  stage: Stage;
  content: string;
  createdAt: string;
};

type Diagnosis = {
  verdict: Verdict;
  riskLevel: "low" | "medium" | "high" | "unknown";
  summary: string;
  missingInfo: string[];
  risks: string[];
  nextQuestion: string;
};

type ProjectState = {
  stage: Stage;
  messages: Message[];
  diagnosis: Diagnosis;
  extractedProject: {
    idea?: string;
    targetUser?: string;
    scenario?: string;
    problem?: string;
    currentAlternative?: string;
    whyAlternativeNotEnough?: string;
    coreMvp?: string;
    cutFeatures?: string[];
  };
  finalPrompt?: string;
};
```

### 8.2 前端流程

```text
用户输入回答
↓
前端将 ProjectState + 当前回答发送给后端
↓
后端调用百炼
↓
后端返回结构化 JSON
↓
前端更新阶段、诊断摘要、下一个问题
↓
如果 finalPrompt 存在，展示最终开发提示词
```

### 9.1 请求

请求体：

- `INVALID_REQUEST`
- `MODEL_CALL_FAILED`
- `MODEL_RESPONSE_PARSE_FAILED`
- `RATE_LIMITED`
- `MISSING_API_KEY`

## 10. 阿里云百炼接入方案

### 10.1 API Key

使用环境变量保存 API Key：

```bash
DASHSCOPE_API_KEY=你的阿里云百炼APIKey
```

不要将 API Key 写入前端代码或提交到 Git。

### 10.2 OpenAI 兼容接口

阿里云百炼支持 OpenAI 兼容接口。北京地域常用配置：

```text
Base URL: https://dashscope.aliyuncs.com/compatible-mode/v1
Chat Completions: https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions
```

如果使用其他地域，应将 Base URL 做成环境变量：

```bash
BAILIAN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
BAILIAN_MODEL=qwen-plus
```

### 10.3 Node.js 调用示例

推荐使用 OpenAI SDK 的兼容模式：

```ts
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.DASHSCOPE_API_KEY,
  baseURL: process.env.BAILIAN_BASE_URL || "https://dashscope.aliyuncs.com/compatible-mode/v1",
});

export async function callModel(messages: OpenAI.Chat.Completions.ChatCompletionMessageParam[]) {
  const completion = await client.chat.completions.create({
    model: process.env.BAILIAN_MODEL || "qwen-plus",
    messages,
    temperature: 0.3,
  });

  return completion.choices[0]?.message?.content || "";
}
```

### 10.4 模型参数建议

第一版建议：

```json
{
  "model": "qwen-plus",
  "temperature": 0.3,
  "top_p": 0.8
}
```

原因：

- 该工具需要稳定判断，不需要过度发散
- 温度过高会导致阶段跳转不稳定
- 后续可为“替代方向建议”单独提高温度

## 11. Prompt 设计

### 11.1 总系统 Prompt

后端每次调用都应带上固定 system prompt：

```text
你是一个严肃、直接、有判断力的项目澄清顾问。

你的任务不是鼓励用户做项目，而是帮助用户判断项目是否真实、是否值得做、第一版应该做什么。

你必须遵守：
1. 不做泛泛聊天。
2. 每次最多提出一个关键问题。
3. 如果用户回答空泛，必须要求补充。
4. 如果项目明显是伪需求，必须直接指出。
5. 不允许一开始就建议开发完整产品。
6. 必须优先判断目标用户、具体场景、现有替代、使用频率、打开新工具的理由。
7. 当信息足够时，必须将项目压缩成 MVP。
8. 最终输出必须能交给 AI 编程工具执行。

你必须返回严格 JSON，不要返回 Markdown。
```

### 11.2 阶段控制 Prompt

每次请求时附加当前阶段说明。

示例：

```text
当前阶段：伪需求审查。

你需要判断：
- 普通 AI 是否能替代
- 微信/表格/备忘录是否足够
- 用户是否有动力打开新工具
- 使用频率是否足够
- 是否只是开发者自嗨

如果缺少关键信息，请只问一个最重要的问题。
如果风险明显，请设置 verdict 为 revise 或 reject。
```

### 11.3 输出 JSON Schema

模型必须返回：

```json
{
  "stage": "initial_diagnosis | need_validation | fake_need_review | mvp_scope | prompt_generation",
  "assistantMessage": "展示给用户的话",
  "diagnosis": {
    "verdict": "pending | pass | revise | reject",
    "riskLevel": "unknown | low | medium | high",
    "summary": "当前诊断摘要",
    "missingInfo": ["缺失信息"],
    "risks": ["当前风险"],
    "nextQuestion": "下一个问题"
  },
  "extractedProject": {
    "idea": "",
    "targetUser": "",
    "scenario": "",
    "problem": "",
    "currentAlternative": "",
    "whyAlternativeNotEnough": "",
    "coreMvp": "",
    "cutFeatures": []
  },
  "finalPrompt": null
}
```

当阶段为 `prompt_generation` 时：

```json
{
  "stage": "prompt_generation",
  "assistantMessage": "已经生成开发提示词。",
  "diagnosis": {
    "verdict": "pass",
    "riskLevel": "low",
    "summary": "项目已收敛到可开发 MVP。",
    "missingInfo": [],
    "risks": [],
    "nextQuestion": ""
  },
  "extractedProject": {},
  "finalPrompt": "完整开发提示词"
}
```

## 12. 阶段跳转规则

不要完全依赖模型自由决定阶段。后端应做基础校验。

### 12.1 推荐规则

```text
initial_diagnosis
  条件：目标用户、场景、问题基本明确
  → need_validation

need_validation
  条件：用户说明当前替代方案、问题频率、替代方案不足
  → fake_need_review

fake_need_review
  条件：伪需求风险低或可修改
  → mvp_scope

fake_need_review
  条件：伪需求风险高
  → 保持 fake_need_review，并要求修改想法

mvp_scope
  条件：一个用户、一个场景、一个核心动作、一个最终产出明确
  → prompt_generation
```

### 12.2 打回规则

如果用户回答出现以下情况，不能进入下一阶段：

- “所有人都可以用”
- “提高效率”
- “帮助学习”
- “让生活更方便”
- “AI 自动解决”
- 只列功能，不说用户场景
- 只说自己想做，不说别人为什么用
- 不能解释现有替代品为什么不够

系统应要求重答，并指出为什么不够。

## 16. 安全与稳定性

### 16.1 API Key 安全

- 只放在后端环境变量
- 不提交 `.env`
- 前端永远不接触 API Key

### 16.2 模型输出解析

模型可能返回非 JSON 内容，因此后端需要：

- 尝试 JSON.parse
- 解析失败时返回 `MODEL_RESPONSE_PARSE_FAILED`
- 前端展示“模型返回格式错误，请重试”
- 后续可加入 JSON 修复逻辑

### 16.3 请求限制

第一版本地使用可不做复杂限制。

如果部署公网，至少需要：

- IP 级限流
- 单次回答长度限制
- 请求体大小限制
- 错误日志

## 17. 开发阶段拆分

### 阶段 A：静态流程原型

目标：

- 不接 AI
- 用固定问题模拟完整流程
- 验证页面体验是否足够清晰

验收：

- 用户能从输入想法走到最终提示词页
- 页面每次只显示一个问题

### 阶段 B：接入百炼 API

目标：

- 后端成功调用阿里云百炼
- AI 能返回结构化 JSON
- 前端能展示下一问题和诊断摘要

验收：

- 输入项目想法后，AI 返回合理追问
- API Key 不暴露在前端

### 阶段 C：伪需求判断优化

目标：

- AI 能打回空泛回答
- AI 能指出普通 AI/微信/表格等替代风险

验收：

- 对明显伪需求能给出 `revise` 或 `reject`
- 不会无条件鼓励用户继续做

### 阶段 D：开发提示词生成

目标：

- 根据前面上下文生成完整开发提示词

验收：

- 提示词足够具体
- 能交给 Codex / Claude Code 启动开发

## 18. MVP 验收标准

第一版完成后，用 5 个不同项目想法测试：

1. 一个明显伪需求
2. 一个模糊但可修改的想法
3. 一个功能过多的想法
4. 一个普通 AI 容易替代的想法
5. 一个相对成立的垂直工具想法

必须满足：

- 能追问具体用户和场景
- 能指出替代品风险
- 能打回空泛回答
- 能压缩 MVP
- 能生成完整开发提示词
- 不出现游戏化表达
- 不默认鼓励所有项目都值得做

## 19. 当前最小开发任务

下一步最适合做：

1. 创建 React + Vite 前端
2. 创建 Express 后端

4. 实现 `/api/project/next-step`
